# セキュリティ

このページでは、脆弱性の報告方法と、信頼できないPDFをpylopdfで処理する方法を説明します。開くときに指定する資源ポリシー、拒否時に返るエラーコード、個々のAPIの上限、内部の防御機構の仕組みを扱います。セキュリティ修正の対象は、PyPIで公開されている最新リリースだけです。

## 脆弱性を報告する { #report-a-vulnerability }

[GitHub Security Advisories](https://github.com/yhay81/pylopdf/security/advisories/new)から非公開で報告してください。公開のIssueは作成しないでください。最初の応答は1週間以内を目安にしています。

## 信頼できないPDFを扱う { #untrusted-pdfs }

pylopdfはRustで書かれ、必須のPython依存関係もありませんが、悪意のあるPDF入力には本質的なリスクが残ります。

### クイックスタート { #quick-start }

!!! warning "資源ポリシーを一式指定する"
    `pylopdf.open()`に`limits=pylopdf.DocumentLimits.web()`を渡してください。このプリセットは、メモリに制約のあるWebワーカーやキューワーカーでユーザーのアップロードを扱うための、保守的な出発点です。

!!! warning "CPU時間の期限を設け、プロセスを隔離する"
    CPU時間の期限は、Worker、プロセス、コンテナのホスト側で強制してください。資源の上限は文書化されたメモリ確保と出力の増大を防ぎますが、実行中のパーサーやインタープリターを経過時間で中断するものではありません。信頼できないファイルの一括処理は、可能であればサンドボックスやコンテナ内で実行してください。

```python
import pylopdf

try:
    with pylopdf.open(
        "upload.pdf",
        limits=pylopdf.DocumentLimits.web(),
    ) as doc:
        facts = doc.complexity
        preview = doc[0].get_pixmap(dpi=144)
except pylopdf.LimitError as error:
    reject_upload(error.code)
```

上限または固定の防御機構が処理を拒否すると、pylopdfは`PdfError`のサブクラスである`LimitError`を送出します。その`code`は下の[コード一覧](#limit-error-codes)にある安定した識別子で、同じ値を`error.args[0]`でも取得できるため、アプリケーションはメッセージを解析せずに分岐できます。

`doc.complexity`は、ページ数、オブジェクト数、ストリーム数、圧縮状態のストリームのバイト数、直接オブジェクトの最大の深さを返します。ストリームを展開せず、レンダラーも呼び出さないため、抽出の前に処理の振り分けを決めるのに適しています。構造と展開の上限は開いた元のファイルを検証するものです。生成した出力が別の信頼境界を越える場合は、同じポリシーで開き直してください。

埋め込まれたJavaScriptは実行されません。設計上サポートしていません。

### 資源の上限 { #document-limits }

`DocumentLimits.web()`は現在、次の上限をそれぞれ独立に適用します。互換性のため、`DocumentLimits`のすべてのフィールドの既定値は`None`（無制限）です。

| 資源 | `DocumentLimits`のフィールド | `web()`の上限 | 拒否コード |
|---|---|---:|---|
| 入力ファイル | `max_file_size` | 10 MiB | `file_size` |
| ページ数 | `max_pages` | 200 | `page_count` |
| 間接オブジェクト数 | `max_objects` | 100,000 | `object_count` |
| 個々の展開済みストリーム（画像のRGBA見積もりを含む） | `max_decompressed_size` | 64 MiB | `decompressed_size` |
| 1つのページ内容ストリーム | `max_page_content_size` | 10 MiB | `page_content_size` |
| 展開済みまたは見積もったストリームの累積バイト数 | `max_total_decompressed_size` | 128 MiB | `total_decompressed_size` |
| 直接の配列・辞書の入れ子 | `max_object_depth` | 64 | `object_depth` |
| 解釈したページ全体での文字のUTF-8累積量 | `max_text_size` | 1 MiB | `text_size` |
| レンダリング・抽出に渡すPDFスナップショット全体 | `max_interpretation_size` | 64 MiB | `interpretation_size` |
| 解釈したページ全体での位置付き文字レコードの累積数 | `max_text_glyphs` | 65,536 | `text_glyph_count` |

用途に応じて別の上限が必要な場合は、`DocumentLimits(...)`を直接作成します。`None`以外の値はすべて正の整数でなければなりません。`max_decompressed_size=`はストリーム単位の上限1つを指定する互換用の短縮形として残っていますが、`limits=`とは同時に指定できません。

`max_interpretation_size`は、hayroが保持済みの入力を最初に読むときと、編集や復号の後、または合成したテキストマークアップの外観付きのレンダリング用コピーを準備するときなど、pylopdfが現在の状態をシリアライズする必要があるたびに適用されます。上限付きの書き込み処理は境界を越える書き込みを拒否し、不完全なレンダラー・抽出用キャッシュを登録しません。互換性のため既定値は`None`で、`DocumentLimits.web()`は64 MiBを設定します。

`max_text_size`を設定すると、プレーンテキスト抽出は組み立て後の正確なUTF-8サイズを事前に検査し、1回の抽出呼び出しの出力を文字量の上限の2倍に制限します。空でない文字は少なくとも1バイトを占め、推定した空白と改行の数は文字数を超えないためです。この出力上限は内部の4,096項目ごとの区切りではなく呼び出し全体に適用され、明示したシーケンスはページ数と4,096の大きい方までしか受け付けないため、同じページ番号を繰り返してもポリシーを回避できません。拒否コードは`text_size`のままで、互換性のための既定値は`None`です。

`max_text_glyphs`は行の組み立て前に保持するレコード数を制限するため、構造化テキストが生成できるブロック、行、スパン、単語、`rawdict`の文字項目の数も制限します。同じページのテキスト解釈と表の解釈は1回分の累積の受け入れを共有し、拒否されたページは上限を消費しません。互換性のため既定値は`None`で、`DocumentLimits.web()`は65,536を設定します。

`get_text("rawdict")`オプションは、ほかの抽出モードと同じ解釈済み文字のキャッシュと、累積の`max_text_size`・`max_text_glyphs`の受け入れを使います。複数の表現を要求しても、キャッシュ済みの同じページが重ねて計上されることはありません。1つの項目が複数文字のUnicode対応を持つことがあるため、文字数とUTF-8の量は別々の上限です。Rust側の生レイアウト用バッファと文字テキストのコピーは失敗を許容する方法で拡張され、ネイティブのメモリ確保が拒否されると、不完全なレイアウトを返さずに`PdfError`を送出します。このポリシーが制限するのは保持する文字データであり、Python辞書の正確なバイト数や、呼び出し側が後で行うJSON・HTMLへのシリアライズではありません。ワーカーから生レイアウトを書き出す場合は、その出力を別に制限してください。

## APIごとの上限 { #api-limits }

個々のAPIは、`DocumentLimits`の有無にかかわらず適用される独自の入力・出力の上限を持ちます。解除方法がある場合も、信頼できる処理にだけ使ってください。

| API | 既定の上限 | 解除方法 | コード |
|---|---|---|---|
| レンダリング | 1ページあたり64メガピクセル | — | — |
| `Pixmap.tobytes()` | エンコード済みPNGで64 MiB | `max_size=None` | `pixmap_output_size` |
| `render_pages()` | エンコード済みPNGの累積で512 MiB | `max_size=None` | `render_output_size` |
| `Page.get_svg_image()` | UTF-8で64 MiB | `max_size=None` | `svg_output_size` |
| `Document.to_markdown()`、`Table.to_markdown()` | UTF-8の累積で64 MiB | `max_size=None` | `markdown_output_size` |
| `Document.tobytes()` | 512 MiB | `max_size=None` | `pdf_output_size` |
| `get_text()`、`to_markdown()`、`render_pages()`、`delete_pages()`、`select()` | 明示的な項目はページ数と4,096の大きい方まで | — | `page_entry_count` |
| `search_for()` | 検索テキストはUTF-8で4,096バイト、ヒットは4,096件 | `max_hits=None` | `search_input_size`、`search_hit_count` |
| `Page.insert_image()` | エンコード済みで64 MiB、展開後のPNGで64,000,000画素 | `max_size=None`、`max_pixels=None` | `image_input_size`、`image_pixel_count` |

| `Shape` | パスの点1,048,576個 | — | `path_point_count` |
| `Page.replace_text()` | 入力はUTF-8で4,096バイト、内容と出力は64 MiB | `max_size=None` | `replacement_input_size`、`replacement_output_size` |

| メタデータ | テキスト1 MiB | — | `metadata_input_size` |

| アウトライン（目次） | ノード・項目65,536個、辺131,072本、テキスト16 MiB、64階層 | — | `toc_entry_count`、`toc_text_size`、`toc_input_size` |

以下の各節で、それぞれの上限の詳細を説明します。

### レンダリングと画像の出力 { #rendering-limits }

- レンダリングは1ページあたり64メガピクセルまでです。
- `Pixmap.tobytes()`のエンコード済みPNG出力の既定の上限は64 MiBです。書き込み処理はPythonの`bytes`を返す前に、境界を越える書き込みを`pixmap_output_size`で拒否します。`max_size=None`で明示的に解除できます。
- `render_pages()`は既定ですべてのページをレンダリングし、明示的な項目はページ数と4,096の大きい方まで受け付け、エンコード済みPNGの累積量を既定で512 MiBに制限します。完了した並列処理の結果は1つのアトミックな上限を共有し、失敗時に部分的なリストは返しません。`max_size=None`で明示的に解除できます。ワーカーの受け入れは、見積もった使用中のラスター・変換用バッファを別に制限し、各ワーカーは4,096ページごとにhayroのキャッシュを作り直します。そのため、アプリケーション側でこれを無制限に並列に呼び出さないでください。
- `Page.get_svg_image()`のUTF-8出力の既定の上限は64 MiBで、PyO3がPythonの文字列を作る前に上限を超えた出力を拒否します。`max_size=None`で明示的に解除できます。hayro-svg 0.8は、pylopdfがこの上限を適用する前に内部でRustの文字列を1つ生成します。
- `Page.get_images()`は列挙した画像またはForm XObjectが4,096個に達すると`image_inventory_count`で停止し、`Page.get_image_info()`は配置4,096個で停止します。`Document.extract_image()`は64,000,000画素と64 MiBのペイロードの上限の下で、コンテンツと色空間の防御機構を通して1つの画像を復号します。Flateで包まれたJPEGをそのまま取り出す場合も、その上限で展開を止めます。

### ページの一括処理 { #page-batches }

ページの一括処理は、1回取得したページ数に照らして項目を検証します。`pages=None`と`insert_pdf()`の全範囲指定は、ページ数にかかわらずすべてのページを対象にします。明示的なシーケンスでは同じページを繰り返せますが、ページ数と4,096の大きい方を超えた最初の項目で生成を止めて`page_entry_count`を返すため、繰り返しても文書全体を1回処理する以上のコストはかかりません。テキスト抽出とレンダリングは呼び出し単位のhayroのキャッシュを4,096項目ごとに作り直し、`max_size`、`max_text_size`などの出力上限は呼び出し全体に適用されます。コアを直接呼び出しても項目の検査は繰り返され、コアのページ取り込みは変更前に重複した取り込み元ページを拒否します。

- `delete_pages()`と`select()`は、PythonとRustの両方で、1回の呼び出しにつきページ数と4,096の大きい方までの項目を受け付けます。そのため、ページを繰り返しても選択結果が文書より大きくなることはありません。イテラブルの読み取りは、上限を超えた最初の項目でオブジェクトグラフを変更する前に停止し、`page_entry_count`を送出します。`insert_pdf()`は取り込み元の全範囲を受け付けます。空の削除はキャッシュ、世代、既存の`Page`ビューを保持します。
- ページの削除と選択では、除外したページへのナビゲーション、それらのページのAcroFormウィジェットとフィールド、タグ付きPDFでそれらのページにしかなかった構造ツリーの内容を、不要オブジェクトの削除の前に整理します。これらの操作は安全な墨消しではありません。任意の独自参照、添付ファイル、メタデータ、そのほかの内容の複製は、それぞれ確認して削除する必要があります。構造ツリーの走査には独自の[上限](#structure-tree)があります。

### テキストの出力 { #text-output-limits }

- `search_for()`は検索テキストをUTF-8で4,096バイトまで受け付け、返す位置情報を既定で4,096件に制限します。Pythonは大きすぎる検索語をPyO3でのコピーの前に拒否し、Rustの境界でも両方の上限を再検査します。信頼できる結果集合は`max_hits=None`で明示的に解除できます。拒否コードは`search_input_size`または`search_hit_count`で、部分的なリストは返しません。
- `Document.to_markdown()`は既定ですべてのページを変換し、明示的な項目はページ数と4,096の大きい方まで受け付け、UTF-8出力の累積量を既定で64 MiBに制限します。見出しの集計とレンダリングの2回の処理を通じて、解釈済みのレイアウト、表、単語は1ページ分しか保持しません。各表にはページ出力を組み立てる前に残りの累積上限が渡されます。見出し、段落、リスト、表は保持する時点で計上され、最後のページは全体のサイズが受け入れられた後に線形時間で組み立てられます。`Table.to_markdown()`を直接呼び出す場合も既定で同じ上限を持ち、結合セルの展開を含むエスケープ後の正確なUTF-8サイズを事前に検査します。上限を超えた変換は部分的な文字列を返しません。`max_size=None`で明示的に解除できます。

### テキスト・画像・描画の入力 { #insertion-limits }

- `Page.insert_image()`は、エンコード済みのJPEG・PNG入力を既定で64 MiB、展開後のPNG入力を既定で64,000,000画素に制限します。ファイル名で指定した入力は、コアの直接呼び出しと同じ上限付きのRustの境界で、GILを解放して読みます。PNGの寸法は展開用の領域を確保する前に検査します。信頼できる処理は`max_size=None`と`max_pixels=None`で明示的に解除できます。
- `insert_text`、`insert_textbox`、`set_form_field`、`set_fallback_font`に明示的に渡したOpenTypeの入力と自動で選ばれたOpenTypeの入力は、既定で64 MiBに制限されます。バッファの入力はPyO3でのコピーの前に拒否し、ファイル名の入力はGILを解放した上限付きのRustの処理で読みます。信頼できる処理は`max_font_size=None`で明示的に解除できます。
- `insert_text()`と`insert_textbox()`は、生成するテキストの入力を既定でUTF-8の1 MiBと、物理行または最終的な折り返し後の4,096行に制限します。`insert_text()`は、`str.splitlines()`が分ける行、またはリストの項目1つを1行として数えます。Pythonは行に分ける前とPyO3でのコピーの前に物理的な入力を検査し、Rustの境界でも再検査して、変更の前に折り返しレイアウトを止めます。テキストボックスのタブ展開は、展開後の文字列を確保する前に量を計算します。信頼できる挿入の入力は`max_text_size=None`で明示的に解除できます。拒否コードは`text_input_size`または`text_line_count`です。AcroFormのテキストと選択肢の外観は、固定の4,096行のレイアウト上限を維持します。UAX #14と書記素のインデックス、行の集合、保持する行のテキストは失敗を許容する方法で拡張されるため、メモリ確保が拒否されても、不完全なレイアウトも文書の編集も外に出ません。pylopdfが行う正規化、書記素の参照、整形済みの行と文字の集合、WinAnsiの出力、入力に由来するテキスト演算子の拡張も失敗を許容します。Standard 14の幅の検査は、エンコードしたテキストのコピーを確保しません。メモリ確保が拒否されると`PdfError`を返し、挿入は文書を変更しないまま、フォームの入力はアトミックにロールバックします。
- `Shape.insert_text()`と`Shape.insert_textbox()`は、呼び出しのたびに同じテキストとフォントの上限を適用します。1つの図形が確定までに保持できるパスの点は1,048,576個までで、点を追加するときとRustの境界の両方で検査し、拒否コードは`path_point_count`です。確定処理は、描画の生成、取り込みの計画、ページの描画先の準備をページを変更する前に終えるため、拒否されても文書は変わりません。
- `Page.replace_text()`は、検索・置換・代替テキストの入力の合計をUTF-8で4,096バイトに制限し、展開したページ内容、フォントのエンコーディングデータ、置換による増加分、最終的なストリーム出力を既定で64 MiBに制限します。確定の前にそのページ専用のストリームを準備するため、複製したページが共有する内容を変更することはなく、一致しない場合やエラーの場合は文書とキャッシュを保持します。呼び出し側のテキストは、事前検査のためにすべてをエンコードせず、PyO3でのコピーの前に逐次数えます。信頼できる入力では`max_size=None`で明示的に解除できます。
- 描画の挿入は、キャッシュの無効化、入力の復号、依存するオブジェクトの作成の前に、ページの`/Contents`の生の配列と参照の連鎖を事前に検査します。生の配列は4,096項目、連鎖は32階層、最終的な配列は1度だけ追加する`q`/`Q`の分離用の組を含めて4,096個のストリーム参照が上限です。失敗しても文書は変更されません。ページへの最初の挿入では、既存の内容を1度復号し、hayroのコンテンツパーサーと同じ読み方で`q`と`Q`の演算子を数えます。分離用の組には、内容中の対応のない`Q`より1つ多い`q`と、内容が閉じずに残す`q`より1つ多い`Q`を入れます。解釈時と同様に、この計数では読み込み時に適用する上限以外の展開上限を再適用せず、復号できないストリームは空として数えます。
- `Page.insert_ocr_text_layer()`は、空でない単語が4,096個を超えるか、UTF-8テキストの合計が1 MiBを超えた時点でイテラブルの生成を止めます。コアの直接呼び出しも同じ上限を適用し、CIDの割り当ては65,535種類目の文字の前で止まり、入力に由来するバッファはすべてPDFを変更する前に準備します。
- 開く処理、`authenticate`、高速なメタデータ読み取り、AES-256での出力に使うパスワードは、PyO3でのコピーやパスワードの鍵導出の前に、UTF-8で127バイトで拒否します。Rustを直接呼び出しても同じ上限を再検査します。拒否コードは`password_input_size`で、保存の拒否は文書の変更や出力の作成より前に行われます。

### フォーム・注釈・ナビゲーション { #structure-limits }

- AcroFormのフィールドツリーの読み取りは、項目・ノード4,096個、辺8,192本、64階層、エンコード済み・展開済み・返却する名前と値の合計1 MiB、選択肢の値4,096個を超える部分的な出力を拒否します。参照の循環は1度だけ訪問し、継承した値は返す末端のフィールドごとに計上します。フォームの入力も同じツリーの上限と、呼び出し側の名前と値の1 MiBの上限をアトミックに適用します。呼び出し側の入力は、フォントの探索、ボタンの検索、ファイルの読み込みの前に`form_field_input_size`で止まります。
- `insert_pdf()`は取り込み先の文書を変更する前に、最上位のフィールド名を1 MiBの名前の上限内で比較し、ページ範囲を指定した場合は、同じノード・辺・ウィジェット・階層の上限で取り込み元のフィールドツリーを走査します。全ページの取り込みはフィールドツリーを走査せずにコピーします。共有のために2つの既定リソースを比較する処理は、オブジェクト4,096個と1 MiBまでしか読みません。それより大きい組は改名します。
- AcroFormのボタンフィールドは、ウィジェット4,096個、通常の外観の状態の項目8,192個、返却する重複のない状態名4,096個、エンコード済み・返却する状態名のテキスト1 MiBを超えると拒否します。フォームの入力は、不足している`Off`とオン状態のキーを変更前に計上します。
- 注釈とリンクの読み取りは、1回の呼び出しで`/Annots`の項目4,096個、またはエンコード済み・返却するメタデータのテキストの合計1 MiBを超える部分的な出力を拒否します。追加は、依存するオブジェクトの作成やキャッシュの無効化の前に、同じページ数の上限、生成するサブタイプとContents・URIの入力の合計1 MiB、ハイライトの矩形4,096個を検査します。呼び出し側のテキストはPyO3でのコピーや矩形の反復の前に`annotation_input_size`で拒否し、ハイライトの反復は4,097個目の項目で停止します。
- 名前付きリンク先の検索は参照の循環を1度だけ訪問し、項目・ノード65,536個または辺131,072本を超える走査を`named_destination_count`、キーのバイト数16 MiBを超える走査を`named_destination_text_size`で拒否し、32階層を超える走査も拒否します。途中で打ち切ったツリーを未解決として黙って報告することはありません。`get_outline()`、`Page.get_links()`、`insert_pdf()`でのリンクの取り込み、ページの削除・選択時の名前ツリーと旧形式の`/Dests`の書き換えはこれらの上限を共有するため、解決できる正しい形式のツリーは整理と取り込みもできます。書き換えでは、保持するリンク先の値を直接オブジェクト1,048,576個（項目あたり16個）とテキスト16 MiBの範囲でコピーします。検索したリンク先の名前は走査中の構造の上限に計上され、アウトラインでは目次のテキスト、名前ツリーではキーのテキスト、リンクではページごとの1 MiBのリンクのメタデータを使います。`Page.get_links()`は最初の名前付き検索でツリーのインデックスを作り、次の編集まではそのインデックスとページのインデックスを再利用するため、すべてのページを読んでも処理時間は線形に収まります。保持するインデックスは同じ項目とキーのテキストの上限内で重複しないキーを1つずつ持ち、拒否したツリーはキャッシュしません。
- 目次の読み取りは反復的なアウトラインの走査を使い、参照の循環を1度だけ訪問し、GILを解放します。ノード・項目65,536個または辺131,072本を超える部分的な出力は`toc_entry_count`で、元テキスト・返却テキストが16 MiBを超えるものは`toc_text_size`で拒否し、64階層やリンク先の間接参照32段を超えるものも拒否します。書き込みも、同じ項目数、階層、タイトルのテキストの上限を、PyO3でのコピーと変更の前に`toc_entry_count`と`toc_input_size`で検査します。ページの削除と選択はアウトラインの上限を共有するため、書き込んだアウトラインは編集できる状態に保たれます。
- ページラベルの番号ツリーの読み取りは、項目・ノード4,096個、32階層、エンコード済みまたは展開済みのスタイルと接頭辞のテキスト1 MiBを超える部分的な出力を拒否します。参照の循環は1度だけ訪問し、書き込みはPyO3でのコピーの前に同じ項目数とテキストの上限を`page_label_input_size`で適用します。

### メタデータ・添付ファイル・XMP { #metadata-limits }

- `Document.metadata`は標準のInfo辞書の8項目だけを復号し、元テキストまたは返却テキストの合計が1 MiBを超えると拒否します。独自の項目はPythonの出力になりません。`peek_metadata(max_file_size=)`はパスまたはバイト列の入力を解析前に拒否でき、返す標準テキストも制限します。`None`は入力の既定である無制限を維持します。書き込みは元テキスト・エンコード済みテキストの合計1 MiBをPyO3でのコピーの前に`metadata_input_size`で事前に検査し、アトミックに適用します。
- `doc.attachments.add()`と`Attachment.write()`はPyO3でのコピーの前に64 MiBを超える入力を拒否し、`Attachment.read()`は展開するフィルターの各層に同じ既定の上限を適用します。大きいと分かっている添付ファイルには`max_size=`を引き上げてください。`max_size=None`は無制限の入力や生成を明示的に許可します。添付ファイルの名前ツリーは、項目・ノード4,096個、32階層、エンコード済みまたは展開済みの名前の合計1 MiBを超えると拒否します。呼び出し側の検索・削除名と、追加時のキー・ファイル名・説明のテキストの合計は、走査やデータのコピーの前に1 MiBで止まり、`embedded_file_input_size`を使います。編集は、インラインのFileSpecを複製する前に、直接オブジェクト4,096個、32階層、直接の文字列・名前・ストリームデータ1 MiBの上限で検証し、ロールバックのために文書全体を複製する代わりにカタログの書き込み先を事前に検査します。
- `Document.get_pdfa_claim()`は、展開するフィルターの各層でXMPの展開後のサイズを既定で1 MiBに制限します。大きいと分かっているパケットには`max_size=`を引き上げてください。`max_size=None`は無制限の生成を明示的に許可します。

### ファイルの保存 { #saving }

- `Document.tobytes()`は、通常の出力、オブジェクトストリーム・相互参照ストリームの出力、暗号化した出力のすべてに、既定で512 MiBのシリアライズ出力の上限を適用します。Rustの書き込み処理は、Pythonの`bytes`に変換する前に境界を越える書き込みを拒否します。`max_size=None`で明示的に解除できます。`save()`は保存先ディレクトリに安全に作成した隣のファイルへストリーム出力し、書き込みが完了した後にだけ指定したパスをアトミックに置き換えるため、シリアライズや置き換えに失敗しても既存のファイルは保たれます。`save()`はメモリ上の出力の上限の対象外です。`garbage`、`deflate`、`use_objstms`などの保存オプションは、その後の入出力が失敗しても、文書化された変更の意味を維持します。
- `Pixmap.save()`は、保存先ディレクトリに予測できない名前で排他的に作成した隣のファイルへ、PNGのエンコード結果を直接ストリーム出力し、書き込みがすべて成功した後にだけ指定したパスをアトミックに置き換えます。完成したPNGをメモリにもう1つ保持することはありません。置き換えに失敗した場合は既存の出力を保ち、一時ファイルを削除します。
- Windowsでは、どちらの保存処理も既存の通常ファイルのDACLと継承の保護設定を維持します。データを書き込む前に一時ファイルへその制限を適用し、セキュリティ記述子をコピーできない場合は保存を拒否します。読み取り専用やロック中の保存先は失敗時も変更されず、失敗した一時ファイルは削除されます。`Document.save()`は相対パスやUnicodeの名前を含む長いWindowsパスを内部で正規化するため、システム全体の長いパスのポリシーを有効にする必要はありません。

## 破損したファイルと修復 { #repaired-files }

寛容な読み込みは、lopdfの相互参照の復旧を使います。`startxref`、`/Prev`、`/XRefStm`のオフセットが64バイト以内でずれている場合は、近くの`xref`キーワードへ移動します。それでも通常の解決に失敗すると、lopdfは行頭のオブジェクトヘッダーと、`/Root`が存在する最新の従来形式の`trailer`から表を再構築します。後のリビジョンのオブジェクトが優先されますが、破損した範囲のオブジェクトは失われることがあります。表より前のバイトが失われたファイルのように、解決した表の項目がカタログやページツリーのルートノードを指していない場合も同じ方法で再構築し、再構築した表がページツリーに届く場合はそれを使います。従来形式のトレーラーを持たない破損した相互参照ストリームのファイルは拒否されます。

どちらの復旧でも`PylopdfWarning`が発生し、`doc.is_repaired`（メタデータの読み取りでは`repaired`キー）が設定されます。レンダリングと抽出は復旧後のオブジェクトグラフを使い、保存するとそのグラフを正規化した相互参照データとともに書き出します。復旧した入力を受け付けられない呼び出し側は、`is_repaired`の文書を拒否できます。19バイトの相互参照項目や、曖昧さのないオブジェクト境界で補正したストリームの`/Length`など、宣言された構造を保つ寛容な処理は報告しません。復旧した文書にも`DocumentLimits`はそのまま適用されます。再構築のコストは事前の走査で制限されます。[相互参照の復旧の事前走査](#recovery-scan)を参照してください。

## 防御機構の仕組み { #how-the-guards-work }

この節では、上記のコードの背後にある固定の防御機構について、正確な挙動を把握する必要がある読者向けに説明します。ネイティブとPyodideのCIは同じ悪意のある入力の回帰テストを共有し、定期的なAtherisのファジングは、不正な相互参照、循環、深いオブジェクト、壊れたストリーム、圧縮爆弾をシードにしています。

### ページツリーの走査 { #page-tree-walker }

??? note "ページツリーのインデックスの詳細"
    すべての公開APIのページのインデックス作成は、1つの反復的なページツリーの走査を使います。ページ数と検索、complexity、レンダリング用スナップショット、目次とリンク、注釈、Formの取り込み、ページ構造の編集もこれに含まれます。再利用されたPage・Pagesオブジェクトと循環、32参照を超える間接の`/Kids`の連鎖、256階層を超える内部のツリー、間接オブジェクトの数を超える辺の数を拒否します。`max_pages`による走査は、上限を超えた最初のページで止まります。ページのポリシーを指定せずに開く場合は互換性を保ち、これらのページツリーの検査を、ページのインデックスを作る最初の操作まで遅らせます。

    ページ数とページの検索は1回の走査で作ったページのインデックスを再利用するため、すべてのページにアクセスしても線形時間に収まります。回転、ページボックス、描画、注釈の編集はページツリーを変えられないため、インデックスを保持します。これらの編集は未使用のオブジェクト番号にだけオブジェクトを追加し、走査が読んだ項目をすべてそのまま残すか、それを示せない場合はインデックスを破棄します。それ以外の編集はインデックスを破棄し、次のアクセスで作り直します。失敗した走査はキャッシュしないため、不正なツリーはアクセスのたびに例外を送出します。

### メモリ確保の失敗 { #allocation-failures }

多くの内部バッファは失敗を許容する方法で拡張されます。アロケーターがメモリの確保を拒否すると、pylopdfは異常終了せずに`PdfError`を送出し、部分的な結果は返しません。たとえば、直接の深さの検証とcomplexityの検査は反復的な走査のスタックを失敗を許容する方法で拡張するため、メモリ確保が拒否されると、部分的な情報を返さずに`PdfError`を送出します。上記のAPIごとの節に、これが当てはまるほかの箇所を記載しています。

### フィルターの連鎖 { #filter-chains }

安全に上限を見積もれないフィルターの連鎖は、楽観的に復号せずに拒否します。pylopdfが管理する上限付きのlopdfの復号処理は、フィルターのリストを生成する前に、16層を超えて連なる`/Filter`も拒否します。

### コンテンツストリームの入れ子 { #content-nesting }

hayroはコンテンツストリーム内の配列と辞書を64階層で読むのをやめ、それより深いオペランドを黙って省きます。pylopdfはその切り捨てを`content_nesting_depth`による拒否に変えます。

??? note "コンテンツストリームの検査が読むもの"
    テキスト抽出、レイアウト、表、検索、図形、画像の読み取り、レンダリング（PNG、ピクスマップ、SVG）、Markdown変換、画像の圧縮がページを解釈する前に、pylopdfはそのページから到達できるコンテンツストリームを復号します。対象は、`/Contents`、リソースにあるForm XObject、注釈とウィジェットの外観（チェックボックスとラジオボタンはすべての状態。hayroが描くのは`/AS`が選ぶ1つです）、ソフトマスクのグループ、タイリングパターン、Type 3の文字描画プロシージャです。配列または辞書が64階層を超えて入れ子になっている場合、ストリームオブジェクトが埋め込まれている場合、検査できないインライン画像の境界がある場合は、そのページを`content_nesting_depth`で拒否します。

    この上限は固定で、`DocumentLimits`の有無にかかわらず適用され、ほかのページは引き続き利用できます。各ページは文書のスナップショットごとに1回だけ検査され、編集すると結果は破棄されます。検査は内容がどの名前を使うかを調べないため、ページのリソース辞書に列挙された項目は、どの演算子も描画しない場合でも対象になります。

### 色空間・シェーディング・関数 { #resource-nesting }

hayroは色空間、シェーディング、関数を深さに制限のない再帰で構築するため、十分に深い連鎖があるとスタックが溢れてプロセスが終了します。pylopdfは、hayroがそれらを構築する前に、そのようなページを`resource_nesting_depth`で拒否します。これらの上限が制限するのはスタックの使用量であり、時間ではありません。ホスト側でCPU時間の期限を強制し続けてください。

??? note "リソースの検査が測るもの"
    hayroは色空間、シェーディング、関数を、コンテンツストリームと同じ種類の深さに制限のない再帰で構築します。IndexedまたはPatternの色空間はそのベースから、SeparationまたはDeviceNの色空間は代替色空間と色調変換から、ICCBasedの色空間は解析できないプロファイルの`/Alternate`から、スティッチング関数は`/Functions`のすべての項目から構築され、Type 4の関数は`{ }`のプロシージャを再帰で解析します。互いを参照する約20,000個の間接オブジェクト、または300,000個の入れ子の波括弧があると、スタックが溢れてプロセスが終了します。

    ページを解釈する前に、pylopdfは、そのページのリソース辞書の`/ColorSpace`と`/Shading`の項目、シェーディングパターン、画像XObject、ソフトマスクのグループ、グラフィックス状態とソフトマスクの転送関数`/TR`・`/TR2`から到達できるものを測ります。色空間と関数の連鎖が16階層より深い場合、またはType 4の関数がプロシージャを64階層より深く入れ子にしている場合は、そのページを`resource_nesting_depth`で拒否します。連鎖には色空間の配列、関数、プロファイルのストリームが数えられます。hayro自身が循環を断つため、自己参照や短い輪はそのまま描画されますが、互いに到達し合う16個を超えるオブジェクトの集まりは拒否されます。共有された部分グラフは1回だけ測るため、検査はどれだけ多くの項目が参照していても各オブジェクトを1回しか読みません。

    これらの上限は固定で、`DocumentLimits`の有無にかかわらず適用され、ほかのページは引き続き利用できます。制限するのはスタックの使用量であり、時間ではありません。各階層で同じ関数を2回参照するグラフや、Separationの色空間の入れ子のように、上限内に収まるグラフでもhayroは指数時間のCPUを要することがあるため、ホスト側でCPU時間の期限を強制し続けてください。

### オブジェクトの入れ子の深さ { #object-depth }

hayroは、それを保持するオブジェクトを含めて64階層を超えて入れ子になった配列や辞書を読まず、そのオブジェクト全体をないものとして扱います。一方、lopdfは100階層まで読みます。ページツリーから継承する属性を含めたページの辞書がそれより深く入れ子になっているページは、操作がそれを解釈するたびに`object_depth`で拒否され、ほかのページは引き続き利用できます。トレーラー、カタログ、ページツリーのルートノードがそれほど深く入れ子になっていても、文書のレンダリングは妨げられません。レンダリングと抽出は深すぎる項目を除いたコピーを読み、編集・保存する文書にはそれらの項目が残ります。それ以外のオブジェクトがそれほど深く入れ子になっている場合は、hayroと同じくないものとして読まれます。`DocumentLimits.web()`は、このような文書を開く時点で`object_depth`で拒否します。

### 構造ツリーの整理 { #structure-tree }

ページの削除と選択で除外したページの構造ツリーの内容を取り除くとき、構造ツリーの走査は、要素と検索用ツリーのノードが1,048,576個、子と項目が4,194,304個、要素が256階層、`/ParentTree`と`/IDTree`が32階層に達すると、文書を変更する前に`structure_tree_count`で停止します。

### レンダラーのパニック { #renderer-panics }

hayroは、誤った数の成分を返すSeparationやDeviceNの色調変換、Patternの色空間のシェーディングなど、一部の不正な色データでパニックします（[LaurenzV/hayro#1546](https://github.com/LaurenzV/hayro/issues/1546)）。hayroにページを解釈させるすべての操作はこのパニックを捕捉し、PyO3の`PanicException`の代わりに`PdfError`を送出します。`PanicException`は`BaseException`から派生しており、`except Exception`をすり抜けてしまうためです。レンダラーの状態は編集時と同じく破棄されるため、以降の呼び出しは最初からやり直され、文書は引き続き利用できます。パニックのメッセージは、Rustが引き続き標準エラー出力に書き出します。

### 相互参照の復旧の事前走査 { #recovery-scan }

lopdfの再構築は、後ろに`endstream`のない`stream`キーワードごとに入力の残りを再走査します。寛容な読み込みとメタデータの読み取りの前に、pylopdfはその作業量を線形時間で見積もり、入力1バイトあたり64バイトに64 MiBを加えた量を超える入力を`recovery_scan_size`で拒否します。これにより、悪意のある入力で復旧が二乗時間になることを防ぎます。実際の破損ファイルでは、その位置にある途切れたストリームは多くても1つです。

## 依存関係の監査 { #dependency-auditing }

CIはプッシュのたびに`cargo audit`を実行し、Rustの依存関係ツリーをRustSecの脆弱性データベースと照合します。

このポリシーのリポジトリ上の正本は[`SECURITY.md`](https://github.com/yhay81/pylopdf/blob/main/SECURITY.md)です。
